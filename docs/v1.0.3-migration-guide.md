# v1.0.3 Migration Guide

## Supported migration boundary

LazyTrae v1.0.3 requires **Node.js LTS 20 or newer** and **Git**. Bootstrap
`lifecycle onboard` only from the verified official origin
`https://github.com/elvinzhao10/LazyTrae.git` (or the equivalent URL without
`.git`). The source checkout is a one-time transport and may be deleted after
promotion.

Use an absolute durable install root:

| Platform | Default install root | Evidence boundary |
| --- | --- | --- |
| macOS | `~/Library/Application Support/LazySeries` | Package behavior verified; host behavior still requires observation. |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/lazyseries` | Package path implemented; Trae Work host behavior unverified. |
| Windows | `%LOCALAPPDATA%\LazySeries` | Package path implemented; Trae Work host behavior unverified. |

```text
<install-root>/
└── LazyTrae/
    ├── active.json
    ├── launcher.js
    ├── releases/<version>-<12-char-commit>/
    ├── receipts/<receipt-id>.json
    ├── rollback/
    ├── staging/
    └── locks/
```

After onboarding, use `node "<install-root>/LazyTrae/launcher.js"`. Do not
restore source-relative, PATH, global, temporary-directory, or cache launchers.

## Filesystem and platform limits

The package fixtures parse the Windows default
`%LOCALAPPDATA%\LazySeries`, including paths with spaces. On POSIX, tests use
real filesystem symlink and hardlink refusal fixtures. Case sensitivity and
maximum path length follow the current filesystem, so tests probe the host
capability and use bounded names rather than assuming macOS, Linux, and Windows
behave alike. These are package-safe fixture checks; this does not simulate
host readiness.

## v1.0.2 to v1.0.3

1. Inventory v1.0.2 managed files and caller-modified or unknown files.
2. Run `lifecycle onboard` for v1.0.3 with absolute install and project roots.
3. Run the stable launcher with `lifecycle status`, then `doctor` and
   `load-check`. These prove package readiness only.
4. Run `init` or `sync`. Preserve every modified or unknown destination.
5. Ask before any host-managed change. Give exactly one GUI/host action, wait,
   and inspect it. Reload/new session and live testing are later actions.
6. Verify one real Skill/command and the core MCP. Without current Computer Use
   or user-supplied evidence, **HOST READINESS: PENDING**.

## Update identity and confirmation

`lifecycle update` resolves the official ref to a full commit SHA. Tag names
are not treated as immutable: if a same-version ref moves, the first update
prints `required_confirmation` without promotion. Review it, then repeat with
`--confirm-revision <full-sha>` only for the intended commit.

One verified previous bundle may be retained. This is recovery evidence, not
permission to edit `active.json`, `rollback/`, or receipts. Preserve blocked
state and report the exact issue.

## Node runtime refresh

The receipt fingerprints the exact Node executable. If Node is moved, replaced,
or upgraded in place, `lifecycle status` reports `STALE_RUNTIME`. There is no
in-place receipt rewrite. Use a fresh verified checkout to run `lifecycle
offboard` without `--yes`, review the exact product-only plan, repeat with
`--yes` after confirmation, and then run `lifecycle onboard` with the current
Node.js LTS runtime.

Project and host state remain outside this refresh. Re-run package checks, then
restart/refresh the host as separate one-action handoffs.

## Scoped offboard and recovery

`lifecycle offboard` removes only exact receipt-owned LazyTrae state. It
refuses modified, unknown, linked, locked, or incomplete product content. It
does not remove the project, another LazySeries product, Trae settings, Work
Skills, MCP registrations, credentials, or host caches.

Remove host registration through its own UI only after separate approval.
Observe a fresh session before reporting host removal. Historical QA feedback
never makes the current host ready.
