# v1.0.3 Adaptive Harness — Change Map

## Overview

v1.0.3 extends LazyTrae with a thin adaptive harness that selects the smallest
sufficient workflow mode for an outcome-based request, composes existing
Skills/agents/commands/MCPs/tools/hooks/verifiers, persists an additive
single-writer adaptive snapshot inside the current loop state, and explains
material choices through the existing status surface. The strategy is surgical:
every change is an **extension** of an existing seam — no replacement
orchestrator, no new command, no new MCP server, no state-store rewrite. The
adapter wraps `detectNeed()` to emit the full adaptive decision per plan
Section 5, maps that decision onto existing workflow surfaces, reuses the
current loop runtime, adds one optional `adaptive` block to the existing
state, and extends `completion-status` output. Seven seams cover the full
adaptive lifecycle; the verification seam is intentionally unchanged.

## Seams

### 1. Request detection

- **File:** `lazytrae-plugin/packages/cli/src/lib/automatic-tooling-detector.js`
- **Current behavior:** Regex-based first-match detector (132 lines). Reads
  `automatic-tooling-policy.js` for the contract. `detectNeed(context)` walks
  the configured capabilities and returns `{capability, reason, evidence}` —
  capability **class** only, with no workflow mode, no `stages`, no
  `responsibilities`, no `approvalRequired`, and no escalation state. No
  provider is activated during classification; `executeFallback` is a separate
  exported function. The detector is the first reverse-ref target of
  `commands/tooling.js` and is the W2.1 seam named in the plan.
- **Exports:** `{ canonicalCapability, detectNeed, executeFallback, redactQuery, runDetector }`
- **Extension strategy:** Add a new `classifyAdaptiveDecision(context)`
  function **in a new sibling module**
  (`lazytrae-plugin/packages/cli/src/lib/adaptive-decision.js`) that wraps
  `detectNeed()` and emits the full adaptive decision shape per plan Section 5:
  `{contractVersion, mode, stages, responsibilities, capabilityClasses,
  verificationLevel, reasons, approvalRequired, fallbackPolicy,
  escalationTriggers}`. The wrapper gathers all signals before selecting, never
  activates a provider during classification, records `reasons` and
  `approvalRequired`, and applies the deterministic ordered policy
  (direct → assisted → planned → orchestrated → long-horizon) per plan
  Section 6. `detectNeed()` itself stays backward-compatible so the existing
  first-match path remains authoritative for `commands/tooling.js`. No scoring
  engine; no replacement of the first-match classifier.
- **Tests that must not break:**
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-detector.test.js`
  - `lazytrae-plugin/packages/cli/test/w0-2-characterization.test.js`
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-policy.test.js`
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-contract.test.js`

### 2. Workflow selection

- **File:** No single file today. LazyTrae has **no automatic workflow
  selection** — workflows are user-driven through explicit command invocation
  (e.g., `/lazy-ulw-plan`, `/lazy-start-work`, `/lazy-ulw-loop`,
  `/lazy-review-work`). The static surfaces are:
  - `.trae/skills/` (17 skills incl. `lazy-ulw-plan/`, `lazy-start-work/`,
    `lazy-ulw-loop/`, `lazy-review-work/`, `lazy-verifier/`)
  - `.trae/commands/` (9 commands incl. `lazy-ulw-plan.md`,
    `lazy-start-work.md`, `lazy-ulw-loop.md`, `lazy-review-work.md`)
  - `lazytrae-plugin/packages/cli/src/index.js` (CLI router; 20 commands)
- **Current behavior:** Explicit user instruction is authoritative. There is
  no internal surface that maps an outcome request onto a workflow mode. Plan
  Section 6 resolution order step 1 ("explicit user workflow") is already
  satisfied by current behavior; steps 2–7 are not implemented.
- **Extension strategy:** Add a thin mapping adapter
  (`lazytrae-plugin/packages/cli/src/lib/adaptive-mapping.js`) that maps an
  adaptive decision onto existing LazyTrae surfaces: `direct` → no special
  workflow, `assisted` → exploration + bounded implementation,
  `planned` → `lazy-ulw-plan` + `lazy-start-work`,
  `orchestrated` → `lazy-start-work` + `lazy-review-work` + `lazy-verifier`,
  `long-horizon` → `lazy-ulw-loop` (existing loop runtime). The adapter
  **selects** surfaces by name; it does not invoke them, does not duplicate
  their execution logic, and does not register new commands. Explicit user
  override (Section 6 step 1) short-circuits the adapter — the named workflow
  remains authoritative.
- **Tests that must not break:**
  - `lazytrae-plugin/packages/cli/test/cli.test.js` (router inventory)
  - `lazytrae-plugin/packages/cli/test/w0-2-characterization.test.js`
  - Any test that asserts the static command/Skill inventory

### 3. Provider/tool resolution

- **Files:**
  - `lazytrae-plugin/packages/cli/src/lib/automatic-tooling-broker.js`
  - `lazytrae-plugin/packages/cli/src/lib/automatic-tooling-policy.js`
- **Current behavior:** The broker (`runCapability`, `parseArgs`) imports
  `automatic-tooling-policy`, `tooling-root`, `tooling-capabilities`,
  `lsp-lifecycle`, `lsp-bridge` and executes the resolved capability. The
  policy loader (`loadContract`, `readConfig`, `resolveCapability`,
  `resolveApproval`, `readLedger`, `writeApproval`, `redactText`) reads
  `contracts/automatic-tooling-contract.v1.json` and is the single source of
  truth for capability-class resolution and approval-gated actions. Both are
  capability-class based; neither emits a `runtimeResolution` map keyed by
  capability class.
- **Exports:**
  - broker: `{ parseArgs, runCapability }`
  - policy: `{ approvalKey, canonicalWorkspace, chooseCredentialReference,
    defaultApprovalPath, defaultConfigPath, defaultToolpackPath,
    decryptCredential, encryptCredential, isOpaqueCredentialReference,
    loadConfig, loadContract, readConfig, readLedger,
    readVersionedDataKey, redactText, resolveApproval, resolveCapability,
    saveConfig, writeApproval }`
- **Extension strategy:** Extend the broker/policy path to emit a
  `runtimeResolution` map (`{capabilityClass → resolved-source}`) that the
  adaptive snapshot can persist per plan Section 11. Apply the capability
  resolution order from plan Section 9 (host-native → repo-native →
  system-local → package-ephemeral → optional-provider → safe-degraded →
  blocked). Honor the authority matrix: read-only and package-owned
  capabilities activate automatically; install/persist/host-settings/
  credentials/remote/browser actions require approval. Fallback behavior
  preserves the same capability class where possible and reports the
  substitution. No second provider lifecycle is introduced.
- **Tests that must not break:**
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-broker.test.js`
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-policy.test.js`
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-policy-cli.test.js`
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-navigation.test.js`
  - `lazytrae-plugin/packages/cli/test/automatic-tooling-contract.test.js`
  - `lazytrae-plugin/packages/cli/test/provider-lifecycle.test.js`
  - `lazytrae-plugin/packages/cli/test/providers-command.test.js`
  - `lazytrae-plugin/packages/cli/test/remote-capabilities.test.js`

### 4. Orchestration

- **Files:**
  - `lazytrae-plugin/packages/cli/src/lib/loop-runtime.js`
  - `lazytrae-plugin/packages/cli/src/lib/loop-store.js`
  - `lazytrae-plugin/packages/cli/src/lib/loop-steering.js`
  - `lazytrae-plugin/packages/cli/src/lib/loop-quality.js`
- **Current behavior:** `loop-runtime.js` is the loop engine (imports
  `loop-steering`, `loop-quality`, `loop-store`, `path-boundary`).
  `loop-store.js` is the state store with atomic writes via `path-boundary`
  (exports `defaultLoop`, `loadLoop`, `saveLoop`, `appendEvent`,
  `requireLoop`, `persistBrief`). `loop-steering.js` handles transitions
  (`cancel`, `pause`, `resume`, `checkpoint`, `steer`, `createGoals`,
  `completeGoals`, `recordEvidence`, `recordReviewBlockers`). The loop
  runtime is the existing long-horizon orchestrator; `lazy-start-work` is the
  boulder orchestrator; there is no separate "adaptive orchestrator" today.
- **Exports:**
  - loop-runtime: existing loop runtime exports (see module)
  - loop-store: `{ defaultLoop, loadLoop, saveLoop, appendEvent, requireLoop,
    persistBrief, ... }`
  - loop-steering: `{ cancel, checkpoint, completeGoals, createGoals,
    criteria, log, pause, recordEvidence, recordReviewBlockers, resume,
    status, steer }`
- **Extension strategy:** The adaptive adapter **calls into** the existing
  loop runtime; no new orchestrator is created. For `long-horizon` mode, the
  adapter selects the loop runtime as the execution authority and writes the
  adaptive snapshot through `loop-store.saveLoop()` (single-writer rule).
  For `orchestrated` mode, the adapter delegates to `lazy-start-work` +
  `lazy-review-work` surfaces. Bounded escalation per plan Section 12
  (≤2 automatic depth increases per decision) is enforced by the adapter,
  not by the loop runtime. The loop runtime itself is unchanged.
- **Tests that must not break:**
  - `lazytrae-plugin/packages/cli/test/loop-runtime.test.js`
  - `lazytrae-plugin/packages/cli/test/loop-quality.test.js`
  - `lazytrae-plugin/packages/cli/test/loop-cli.test.js`
  - `lazytrae-plugin/packages/cli/test/mcp-context.test.js`
  - `lazytrae-plugin/packages/cli/test/w0-2-characterization.test.js`

### 5. State persistence

- **Files:**
  - `lazytrae-plugin/packages/cli/src/lib/loop-store.js` (state store)
  - `lazytrae-plugin/packages/cli/src/mcp/state-access.js` (MCP-side writes)
  - `lazytrae-plugin/.lazytrae/schemas/active-loop.schema.json` (319-line schema)
  - `lazytrae-plugin/packages/cli/templates/state/active-loop.json` (install template)
- **Current behavior:** Schema pins `version` to `{minimum: 1, maximum: 1}`
  (line 9); `additionalProperties` is not forbidden. Required fields are
  `version, created_at, updated_at, brief_path, goals_path, ledger_path,
  goals`. No `adaptive` field exists. `loop-store.js` performs atomic writes
  via `path-boundary`; `state-access.js` serializes MCP writes through
  `withFileLock(filePath, fn)` (exports `assertSafeWrite`, `readJSON`,
  `writeJSON`, `withFileLock`, `getLoopState`, `getActiveWork`). The template
  uses `schema_version: 1` and `version: 1`.
- **Exports:**
  - loop-store: `{ defaultLoop, loadLoop, saveLoop, appendEvent, requireLoop,
    persistBrief, ... }`
  - state-access: `{ assertSafeWrite, readJSON, writeJSON, withFileLock,
    getLoopState, getBoulderState, getSessionsState, listEvidence,
    getActiveWork, ... }`
- **Extension strategy:** Add an optional `adaptive` block per plan
  Section 11 (`{version, decisionId, requestDigest, mode, stages,
  currentStage, responsibilities, capabilityClasses, runtimeResolution,
  reasons, escalationCount, revisionMarker, blocker, nextAction}`) as an
  additional property in `active-loop.schema.json` — **no `version` bump**
  (still `1`). Update `templates/state/active-loop.json` with
  `"adaptive": null` default. Enforce the single-writer rule: only the
  adaptive orchestrator writes `adaptive`; MCP writes through `withFileLock`
  continue to serialize. v1.0.2 state without `adaptive` must continue to
  load. No new lock, no compare-and-swap, no cross-process coordination.
- **Tests that must not break:**
  - `lazytrae-plugin/packages/cli/test/state-contracts.test.js`
  - `lazytrae-plugin/packages/cli/test/security.test.js`
  - `lazytrae-plugin/packages/cli/test/namespace-migration.test.js`
  - `lazytrae-plugin/packages/cli/test/loop-runtime.test.js`
  - `lazytrae-plugin/packages/cli/test/mcp-context.test.js`

### 6. Status/explanation

- **File:** `lazytrae-plugin/packages/cli/src/commands/completion-status.js`
- **Current behavior:** A 20-line command that imports `formatCompletionStatus`
  and `getCompletionStatus` from `completion-gates.js`, runs the gates against
  the detected repo root, prints the formatted result, and exits 0 if ready
  or 1 otherwise. No adaptive explanation is emitted. The command is the
  existing user-facing status surface and is the natural place to surface
  adaptive decisions without adding a new command (per plan Section 13 and
  W2.4 acceptance criterion "no new command added").
- **Exports:** `{ run }`
- **Extension strategy:** Extend the output of `completion-status` with an
  adaptive explanation block per plan Section 13 (mode, selected stages,
  responsibilities, capabilities, not-selected, approval required). The
  extension is additive — current output stays intact for non-adaptive
  contexts. The command reads the `adaptive` block from loop state (if
  present) and renders it concisely. No new command is added; the CLI router
  inventory in `src/index.js` stays unchanged.
- **Tests that must not break:**
  - `lazytrae-plugin/packages/cli/test/completion-gates.test.js`
  - `lazytrae-plugin/packages/cli/test/cli.test.js`
  - `lazytrae-plugin/packages/cli/test/w0-2-characterization.test.js`

### 7. Verification

- **File:** `lazytrae-plugin/packages/cli/src/lib/completion-gates.js`
- **Current behavior:** Exports `getCompletionStatus(repoRoot)`,
  `formatCompletionStatus(result)`, `validateEvidencePaths(repoRoot, paths)`,
  plus `detectRepoRoot`, `readJSON`, `resolveEvidencePath`. Inspects boulder
  and loop state, validates evidence paths, and produces a `{status, reasons}`
  result. Used by `verify`, `handoff`, `completion-status` commands and by
  MCP handlers (`handlers-evidence.js`, `handlers-handoff.js`).
- **Exports:** `{ detectRepoRoot, readJSON, resolveEvidencePath,
  validateEvidencePaths, getCompletionStatus, formatCompletionStatus }`
  (plus internal helpers)
- **Extension strategy:** **No changes needed.** The adaptive harness calls
  the existing verification gates; it does not introduce a second verifier,
  a new evidence format, or a new completion model. Stale-snapshot handling
  (plan Section 11) is enforced by the adapter when it reads the
  `revisionMarker` — not by the verifier. Evidence freshness (W4.6) is
  achieved by re-running `getCompletionStatus` after relevant implementation
  changes, not by adding an evidence-lineage database.
- **Tests that must not break:**
  - `lazytrae-plugin/packages/cli/test/completion-gates.test.js`
  - `lazytrae-plugin/packages/cli/test/w0-2-characterization.test.js`
  - Any MCP handler test that asserts `getCompletionStatus` behavior

## Risk callouts

- **Detector currently has no workflow-mode concept** — adding it is the
  central change. The wrapper approach (`classifyAdaptiveDecision` in a new
  sibling module) keeps `detectNeed()` backward-compatible and lets the
  existing `commands/tooling.js` path continue to work, but the wrapper must
  not introduce a scoring engine or mix classification with provider
  activation (plan Section 6, W2.1 "Must NOT do").
- **State schema allows additive `adaptive` block without version bump** —
  verified: `active-loop.schema.json` line 9 constrains `version` to
  `{minimum: 1, maximum: 1}` and does not forbid `additionalProperties`.
  The `adaptive` block must remain optional and additive; v1.0.2 state
  without it must continue to load.
- **MCP writes serialized via `withFileLock`** — single-writer rule is
  achievable: the adaptive orchestrator writes `adaptive` through
  `loop-store.saveLoop()` (which uses `path-boundary` atomic writes), and
  MCP-side writes continue to serialize through `state-access.withFileLock`.
  No new lock or compare-and-swap is needed.
- **Explicit-override short-circuit must come first** — plan Section 6
  resolution order step 1 is authoritative. The adapter must check for an
  explicit named workflow **before** applying the ordered policy, or it will
  silently downgrade user intent (W4.1 negative test).
- **Bounded escalation is adapter-enforced, not runtime-enforced** — the
  loop runtime does not know about escalation counts. The adapter must track
  `escalationCount` in the `adaptive` block and refuse to escalate beyond 2
  automatic depth increases per decision (plan Section 12).
- **Cross-repo byte-identical vendoring** — the contract and fixtures must
  be byte-identical between LazyTrae and LazyBuddy. Any host-specific name
  leaking into the contract is a defect (W1.1 negative test).
- **No source files modified in W0.3** — this wave produces the change map
  only. All source edits happen in W1.1+ and W2.1+.
