# LazyTrae v1.3.0: supported route

v1.3.0 is a published stable release. This historical guide documents its route; it does not establish current host activation. v1.3.1 is now the latest published stable release; this page remains the v1.3.0 historical route.

v1.3.0 adds dual activation: an explicit start-work command and a plain
natural-language implementation request converge on the same execution
authority and gates. Explanation, quoted-command, or explicit plan-only
requests never mutate product files.

For the v1.3.0 route, **Node.js LTS 20 or newer** and **Git** must be available
on PATH. Run every command through the durable launcher below, never a global
package lookup.

1. Clone the published v1.3.0 release tag and promote it through the
   durable lifecycle:

   ```bash
   git clone --branch v1.3.0 https://github.com/elvinzhao10/LazyTrae.git
   node "<checkout>/lazytrae-plugin/packages/cli/bin/lazytrae.js" lifecycle onboard \
     --source https://github.com/elvinzhao10/LazyTrae/releases/tag/v1.3.0 \
     --install-root "<absolute-install-root>" --project "<absolute-project-root>" --json
   ```

2. Run the stable launcher, never a global package lookup:

   ```bash
   node "<install-root>/LazyTrae/launcher.js" lifecycle status \
     --install-root "<install-root>" --project "<project-root>" --json
   node "<install-root>/LazyTrae/launcher.js" --root "<project-root>" \
     load-check --host "<ide|work|cli>"
   ```

3. Use the host-specific handoff. IDE and Work use the emitted local core MCP
   JSON only through the visible documented/manual settings surface. Work also
   uses `work install` for the selected desktop/local skill route. CLI stays
   observe-only unless the current build exposes a documented/manual MCP
   registration surface.

4. MCP declarations are validated before they are trusted. Every declared
   server must use a space-free `command`; a declaration that violates this
   reports a typed error naming the server and the remediation. Only
   `${workspaceFolder}` is expanded as a documented variable; an unsupported
   variable is reported rather than silently passed through.

5. Project-level MCP is a host opt-in. `init` prints the enable-and-confirm
   step for the selected host and states that enabling the toggle is a host
   setting, not an observation that a server is running. It never reports host
   readiness from generated files alone.

6. Read the printed next action from `status` before claiming readiness.
   Package readiness and host readiness are separate authorities, and each host
   reports its own remaining step.

7. Reload or open a fresh session. Package checks, generated files, and a
   probe are package evidence only. Host readiness requires a visible LazyTrae
   Skill or command and a live `lazytrae` core MCP connection in that session.

Until a host is observed in a fresh session, report **HOST READINESS: PENDING**
for every route above.

Do not publish a marketplace package, upload project data, or invent a
universal TraeCode CLI registration command.
